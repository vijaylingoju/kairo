## 1. Summary

| Metric | Baseline (14:52) | **Final (15:50)** | Final, repeat run (15:52) | Rules + CLIP only (15:53) |
|---|---|---|---|---|
| Scenarios passed (of 41) | 10 | **39** | 39 | 34 |
| Correct photo ranked #1 | 34 | **39** | 39 | 35 |
| Mean precision (share of returned photos that are right) | 0.35 | **0.98** | 0.98 | 0.86 |
| "Not in gallery" queries correctly returning nothing | 0 / 5 | **4 / 5** | 4 / 5 | 4 / 5 |
| Answer cards correct (PAN, PNR, seat, amount…) | 8 / 9 † | **9 / 9** | 9 / 9 | 8 / 9 |
| Median search time | 2.75 s | 3.07 s ‡ | 3.15 s | **0.13 s** |

† 8 of 9 values were right (the flight seat came from the train ticket), but every baseline answer query still failed overall because of the extra photos returned.
‡ 15 of the 41 queries now skip Gemma via the new fast path and finish in **0.11–0.17 s**. The other 26 take about 3.2 s (median) because Gemma interprets the question.

**In one line:** Gemma 4 E4B reads photos well (all 18 test photos in the right category, rich tags). The baseline's weakness was the **search logic around it**, which returned the right photo first but padded the results with wrong ones. After 17 fixes, search returns almost exactly the right photos, answers every document question correctly, and the app is **genuinely offline**: the INTERNET permission is removed.

**Pass rule:** the correct photo is #1, all relevant photos are returned, at least 50% of the returned photos are relevant, and the answer card (if expected) contains the right value. For negatives, **zero results**.

### 2.3 Also tested end to end
- **Live indexing:** 5 new photos pushed while the app was running.
- **Clear all data & start fresh:** both through the UI button and through the harness.
- **Full re-index:** timing for all 18 photos.
- **Privacy:** permissions in the APK and on the device.
- **Resilience:** screen-off behaviour and a runaway Gemma generation.

### 2.4 How it was run (repeatable)
A **debug-only** receiver (`app/src/debug/.../EvalReceiver.kt`, protected by the `DUMP` permission so only adb can trigger it, and absent from release builds) runs the real search and indexing code. It writes one JSON result per query.

```
powershell -ExecutionPolicy Bypass -File tools/eval/run_eval.ps1 -Label final           # with Gemma
powershell -ExecutionPolicy Bypass -File tools/eval/run_eval.ps1 -Label nollm -NoLlm     # rules + CLIP only
powershell -ExecutionPolicy Bypass -File tools/eval/analyze_adj.ps1 -RawDir <pulled eval folder>
```
Results are saved to `tools/eval/results/` (**git-ignored: it contains OCR of real personal documents**).

## 3. How Gemma 4 E4B performs

### 3.1 What it does well ✅
| Area | Evidence |
|---|---|
| **Categorising photos** | 18/18 in the right category after fixes, including the tricky ones: a restaurant bill that says "Paid by UPI" was still labelled `bill_invoice`, and the IRCTC ticket was labelled `train_ticket` |
| **Describing photos** | "A plate of stuffed bread rolls with green peppers and cheese", "A person holding a cone of ice cream in front of a point of sale screen", "A close-up of a man with a dramatic expression and makeup" |
| **Tags that search can use** | Specific *and* general tags, e.g. `golden retriever, dog, puppy, pet, animal` and `mcdonalds, french fries, fast food`. **Tag agreement turned out to be the most reliable search signal**, stronger than CLIP (§5.3) |
| **Movie-ticket fields** | Title, date, show time, venue, seats and amount were correct on 3 of the 4 movie tickets in the first pass |
| **Understanding questions** | It fixes typos ("golden retreiver"), translates Telugu and Hindi into English keywords, and turns "which theatre is Irumudi in" into `field=venue` |
| **Stability** | 0 generation timeouts across the final runs (78 query calls + 18 photo reads after the fix); the repeat run gave identical scores (39/41) |
| **Speed on the iQOO 15 GPU** | Loads in 5.4–9.2 s (cached vs cold). About 4.7 s per normal photo, 7–12 s per text-heavy screenshot or document (image + OCR text in, ~200 tokens of JSON out) |

### 3.2 Where it's weak ⚠️
| Weakness | Evidence | How we handle it |
|---|---|---|
| **Copies misread digits and letters** | It relies on OCR: `WMWFP43` was read as `WMWEP43` (F→E, an ML Kit error, still there at full resolution) | Regex + grounding + O→0 repair (§4). F→E is still open |
| **Skips fields it could read** | DC ticket: seats, date and amount were in the OCR text but missing from Gemma's JSON | Regex fallbacks for movie seats and show time now fill them |
| **Picks the wrong value when several look similar** | Took the status-bar clock ("12:13") as a ticket time, and "4LA sleeper" (an upgrade option) as the bus seat | Status bar removed from OCR; bus seat still wrong (open) |
| **Wrong kind of ID** | Put a bill's GSTIN and a ticket's PNR into `id_number`; turned "Male xxxx8271" into an ID | ID numbers only on ID cards and only if regex-valid |
| **Tags vary between re-indexes** | The McDonald's photo was tagged "fast food" in one index and not in the next, so the "fast food" query result changed | Open: see §6 |
| **Slow for query understanding** | About 2.5–3.3 s per question | Fast path skips Gemma when the rules fully understand the question (15/41 queries → 0.11–0.17 s) |
| **Can run away** | During testing, one query ("Maa Inti Bangaaram seats") **never finished generating**, blocking every later search | Every call is now capped (160/400 tokens) with a watchdog that cancels after 12 s / 45 s |

### 3.3 Is Gemma worth it at query time? (rules + CLIP only vs with Gemma)
| | Rules + CLIP only | With Gemma |
|---|---|---|
| Passed | 34 / 41 | 39 / 41 |
| Median time | **0.13 s** | 3.07 s |
| Queries only Gemma solved | – | Telugu, Hindi, "doggo", "icecream", "which theatre is Irumudi in" (the venue field) |

**Conclusion:** keep Gemma for queries in other languages, slang or free-form questions, and **keep the fast path for everything else**. Visual and document queries score the same without Gemma and are about 25× faster.

## 4. Issues found and fixed (17)

| # | Issue | Found by | Root cause | Fix | Verified |
|---|---|---|---|---|---|
| 1 | **App could reach the internet** | Privacy check | ML Kit adds Google `datatransport` (usage logs), which merges in `INTERNET` | `tools:node="remove"` on INTERNET in the manifest | APK has 0 INTERNET permissions; app indexes normally; 0 crashes |
| 2 | **Runaway Gemma generation blocked all searches** | Calibration run hung for 3.5 min on A09 | No output cap, no timeout; one call held the lock forever | `maxOutputToken` cap + watchdog → `cancelProcess()` | 96 bounded calls, 0 timeouts, no hangs |
| 3 | "Hub" photos matched every query | Baseline: puppy/person/PAN scored 0.21–0.28 for *everything* | CLIP gives some images high similarity to all text | Score relative to each photo's own baseline (10 generic prompts) + tag agreement | Precision 0.35 → 0.98 |
| 4 | Every "not in gallery" query returned photos | N01–N05 all failed | Cut-off was relative to the best match only | CLIP-only results need adjusted score ≥ 0.08; no understanding → no results | 0/5 → 4/5 |
| 5 | Document queries padded with photos | "restaurant bill" → bill + PAN + puppy + person | CLIP extras added to document results | Found by text → stay in category; rare name narrows ("Irumudi") | Document 0/8 → 8/8 |
| 6 | "Has the field" counted as a match | "what's my PNR" → 9 photos | +1 for any photo with a booking ID | Field only breaks ties | Answer 0/9 → 9/9 |
| 7 | Answer taken from the wrong photo | "seat for my flight" → `B2` (train seat) | First photo *with* a seat, not the best match | Answer only from the top-scoring photo(s) | A03 → `14C` |
| 8 | Bus ticket labelled train | Index dump | No `bus_ticket` category; LLM calls all PNR tickets trains | New category + OCR bus signals (bus, boarding point, INTRCITY) | `bus_ticket` ✅ |
| 9 | Status-bar clock saved as a field | `"time":"12:13\n"` on screenshots | OCR read the status bar; regex `\s?` grabbed a newline | Skip the top 4% of screenshots in OCR; values trimmed | No clock times left |
| 10 | O/0 confusion in booking IDs | `SRYROO01009831` | OCR reads 0 as the letter O | O→0 inside digit runs (after grounding) | `SRYR0001009831` ✅ (unit-tested) |
| 11 | Flight seat and PNR missing | Boarding pass fields | Seat regex didn't know `14C`; PNR regex only 10 digits | Flight seat and alphanumeric PNR patterns | `14C`, `KX7Q2M` ✅ |
| 12 | Train berth wrong, date missing | `B2`, no date | OCR: "B2**I** 34", "15-**0**ct-2026" | Tolerant patterns + `CNF/B2/34` status line + `0ct`→`Oct` | `B2 / 34`, `15-Oct-2026` ✅ |
| 13 | Movie fields missing (DC ticket) | Gemma skipped them | – | Regex fallbacks: "PREMIUM - H13, H14", "Fri, 07 Aug \| 09:30 PM" | DC ticket complete ✅ |
| 14 | Wrong "ID numbers" | GSTIN / PNR / "Malexxx8271" as `id_number` | LLM copies nearby text | IDs only on ID cards and only if regex-valid; masked Aadhaar → `XXXX XXXX 8271` | ✅ unit-tested |
| 15 | Slow searches | Every query ~2.8 s | Gemma called on every query | Fast path when rules are confident | 15/41 queries in ≤0.17 s |
| 16 | Short-word prefix junk | "red car" → 14 photos (`car*` matched "card") | FTS prefix match for every word | Prefix only for words of 5+ letters | 14 → 1 result |
| 17 | Non-English / slang returned everything or nothing | Hindi "कुत्ता" → 18 photos; "doggo" → 0 | No criteria → keep all; slang kept as keyword | Prompt: translate + dictionary words; fall back to Gemma's visual phrase; no understanding → no results | Both pass ✅ |

Also fixed in the test tooling: screen-off froze the app (the runner now wakes the phone), a wrong output path, a PowerShell parameter bug, and `goAsync()` for background runs.

**Unit tests:** 14 JVM tests (4 CLIP tokenizer + 10 field extraction built from the real OCR strings above), all passing.

## 5. Indexing performance (iQOO 15)

### 5.1 Speed
| Step | Where | Time |
|---|---|---|
| CLIP embedding (pass 1, makes a photo searchable) | GPU + CPU | **75–300 ms per photo**; 18 photos in about 4 s |
| ML Kit OCR | CPU | 40–100 ms per photo (screenshots now at full resolution) |
| Gemma 4 E4B read (pass 2) | GPU | 4.6–7.4 s per normal photo · 7.3–12.7 s per document or screenshot |
| **Full re-index, 18 photos** | – | **227 s → 157 s** (same photos, after fixes) |
| **Live indexing** (5 photos dropped in while the app runs) | – | **Searchable in about 2 s** (CLIP); categories and fields after 26–60 s (Gemma queue) |
| Gemma load | GPU | 5.4 s (cached) / 8.7–9.2 s (cold) |

### 5.2 Resources
| | |
|---|---|
| App memory with both models loaded | about **2.0 GB PSS** (native 806 MB, graphics 520 MB); the phone has 16 GB |
| Model files | 3.66 GB (Gemma) + 0.60 GB (CLIP) in the app's external folder |
| Gemma GPU caches | about 34 MB in the app cache |
| Index database | 155 KB for 18 photos (about 8.6 KB per photo, including the 2 KB CLIP vector) |
| APK (debug) | 158 MB (LiteRT-LM + LiteRT + ML Kit native libraries) |

### 5.3 CLIP findings (calibration, `analyze_adj.ps1`)
- A correct photo beat the best wrong photo by only **0.003–0.022** (adjusted score).
- A non-existent concept ("snowy mountains") still scored **0.069** on a movie still, higher than most real matches.
- So **CLIP ViT-B/16 can't decide on its own what belongs in the results** on this gallery. It's good for *ranking* and as a confirmation; **Gemma's tags decide inclusion**.
- A stronger image-text model (SigLIP 2, or a bigger CLIP) is the main lever for visual-only search (§7).

## 6. Known issues (not fixed yet)

| # | Issue | Impact | Proposed fix |
|---|---|---|---|
| K1 | **"red car" returns the McDonald's photo** | 1 false positive: "red" (packaging) matched, "car" didn't | Require CLIP agreement when only some of the query words match |
| K2 | **"fast food" returns all 7 food photos** | Gemma's tags vary between re-indexes; this time "fast food" wasn't tagged, so the fallback phrase "a fast food meal" matched all meals | Fixed tag set / lower temperature for indexing; exclude generic words ("meal") from the fallback |
| K3 | **OCR F→E** (`WMWEP43` should be `WMWFP43`) | Wrong booking ID on one ticket | Second OCR pass on the cropped ID region, or ask Gemma to read just that crop |
| K4 | **Bus seat = "4LA sleeper"** | Wrong seat on the bus ticket (it's an upgrade option) | Bus-specific seat rule, or drop seats not near a "Seat" label |
| K5 | **Visual-only search is conservative** | A photo whose tags don't contain the query word needs a very strong CLIP score (≥0.08), so some real matches may be hidden | Better CLIP model; show "closest matches" as a separate, clearly marked row |
| K6 | **Screen off → app frozen** | While the screen is off, an app not running a WorkManager job is frozen by Android (seen: an "8-minute" Gemma load) | Only load Gemma inside the indexing job or while visible; don't warm up in the background |
| K7 | **Foreground notification not allowed from background** | `ForegroundServiceStartNotAllowedException` (Android 16); indexing still runs, but without the notification and with the 10-minute job limit | Start indexing from the visible app, or use a user-initiated data-transfer job |
| K8 | **ML Kit still logs usage events locally** | `datatransport` DB (98 KB) grows; it can't upload anything (no INTERNET) | Disable ML Kit analytics components / periodically clear |
| K9 | **Small test set** | 18 photos, 41 queries; thresholds may not generalise | Grow to 100+ real photos (animals, places, people, receipts) and re-run the same harness |
| K10 | **Gemma query latency ≈ 3 s** | Noticeable when used | Stream the rules-only result instantly and refine it when Gemma finishes; or a smaller model just for queries |

## 7. Recommendations (next steps, in priority order)
1. **Grow the test gallery** to 100+ real photos and re-run `run_eval.ps1`. This is the most important step before tuning anything further (K9).
2. **Fix K1/K2**, then commit. Both are small changes in `SearchEngine.kt`.
3. **Show instant results:** return the rules + CLIP results in about 0.13 s, then update when Gemma finishes (K10). The eval shows rules + CLIP alone already get 34/41 right.
4. **Better visual model:** evaluate SigLIP 2 or a larger CLIP with the same harness (K5, §5.3). If it runs on the Hexagon NPU, it also backs up the "NPU" claim on slides 5 and 8.
5. **Indexing robustness:** load Gemma only while indexing or visible (K6); user-initiated job for big galleries (K7).
6. **Demo readiness:** fingerprint lock + masking for ID numbers; UI refinement (checklist §8).
